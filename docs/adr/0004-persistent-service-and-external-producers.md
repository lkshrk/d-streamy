# 0004 — `dstreamy serve` with external producers, and an OBS output plugin

Status: accepted (2026-11-06; proposed 2026-10-23). Amends 0001 (external producers) and 0003 (the session lock applies to `daemon` too). Linux and macOS implementations are present; the parts listed under Deferred are not. Available workflows are not evidence that a release or hardware check ran.

## Context

OBS Studio already captures and encodes what streamers want to show, and many stream to Twitch or similar at the same time. D-Streamy should take OBS's encoded H.264 and Opus and stream them to Discord Go Live, next to that normal stream, without re-encoding in Rust and without putting Discord code into OBS.

The existing Rust pieces fit: `Session` takes a `Box<dyn CaptureSource>`, the pump sends pre-encoded Annex B and Opus, and `dstreamy daemon` (ADR 0003) already exposes the commands over stdio. But `daemon` exits on stdin EOF and owns one parent, and a session ends when its source ends. An OBS restart must not end the stream.

External facts this ADR relies on are pinned in `docs/specs.md`. A behaviour with no source there is not relied on and not mocked: it is either measured in CI, or made configurable and measured once against real Discord.

## Decision

### Service

- **`dstreamy serve`** is a long-running process that exits only on `shutdown` or a signal. A client disconnecting never stops it or the session.
- **The command engine is shared.** The command handling moves out of `daemon.rs` into one engine that `daemon` (stdio, protocol 1, exits on EOF) and `serve` both drive. The target `external` is enabled only in `serve`. `update` on an `external` session is `invalid_params`, because the producer owns the encoder settings.
- **Producer settings drive the announced video.** A producer's `hello` declares codec, width, height and fps. The engine starts an `external` session with codec H.264, and when an attachment's values differ from what is announced it calls `Session::update_video`, so op 12 always matches the media. A producer whose values `Resolution` or `Fps` reject (odd or larger than 1920×1080; fps other than 15, 30 or 60) is refused with `incompatible`.
- **One account, one session.** The same token in two processes evicts the other (`StopReason::VoiceTakenOver`). Whichever of `stream`, `tui`, `daemon` or `serve` has a live session holds `File::try_lock` on `<config-dir>/session.lock`. The holder's PID goes in a separate `session.pid`, because an exclusive `LockFileEx` lock blocks reads on Windows. A second session fails with `already_running` and names the PID. This changes `daemon`: `start` can now fail with `already_running` because of another process. The error code already exists in protocol 1, so the wire format and fixtures don't change. The lock is released when the session state becomes `Stopped`, so a session that stops on its own frees it too. The lock is per config directory: two processes with different `--config-dir` values and the same token are not protected. ADR 0005 moves the lock into each saved account (`accounts/<name>/session.lock`), so two accounts can stream at once.

### External source

- **`ExternalSource: CaptureSource`** is fed by attachments. The session does not know about producers. Its frame receiver stays open across producer swaps and closes only when the grace period runs out (`[serve] grace_secs`, default 30) or the session stops. The grace period runs both while no producer is attached and while an attached producer has stalled (`[serve] stall_ms`, default 2000). `grace_secs` is at most 3600 and `stall_ms` between 500 and 600 000. A control `start` may carry `grace_secs`, under the same bound, to replace the configured grace for that session only; out of range, or on a target other than `external`, it is `invalid_params`. The protocol 1 daemon ignores it, as it ignores any field it does not know. A serve without the `start_grace_secs` feature ignores it too, so a client that depends on it checks `features` first.
- **Attachments can come early.** The source exists from the control `start`, so a producer may attach before Discord is connected. Frames before `CaptureSource::start` are dropped. The grace period starts counting only at `CaptureSource::start`, because connecting can retry with backoff. `stop` followed by `start` on the same object keeps the attachment and timeline, but every explicit `CaptureSource::start` grants a full fresh grace period. A normal Discord stream reconnect retains the source and pump instead of calling stop/start. With `grace_secs = 0`, a producer must attach before the source's first tick; absence expires immediately.
- **`ExternalSource` owns the timeline.** The pump's `Timebase` is created once per pump and is not involved in producer swaps. On a backward jump of more than 1 s it rebases each track separately, which is exactly what must not happen. So `ExternalSource` emits its own monotonic `u64` timeline, and the pump never sees a backward jump.
  - Producer pts are signed (OBS pts can be negative). The first pts of the first attachment maps to 0, and anything still negative is clamped.
  - A new attachment's first frames are held until both tracks have sent one (at most 500 ms; a single-track producer then goes ahead alone), or before pushing a frame would exceed the queue capacity or 64 MiB of held payload. One offset is then applied to both tracks: the smallest that keeps each track at or after its own last pts plus the wall-clock time since that frame arrived, so a stall before the detach counts as elapsed time too. On a fresh timeline this maps the earlier first pts to 0. Taking the larger last pts minus the smaller first pts instead would push both tracks ahead of the clock by the producer's A/V skew on every reattach (about 21 ms with Opus priming), and that adds up. The pump stamps RTP from pts without wall-clock pacing, so per-track rebasing would shift audio against video by the length of a gap.
  - Idle frames follow the same clock and don't count towards the offset.
- **After a reattach, video resumes at a keyframe.** Audio resumes at once. A lossless stall does not close an already-open video gate, so the next delta remains usable. Actual loss closes the gate until a real validated keyframe arrives; it never forwards undecodable deltas to escape the gate. If none arrives within 2 s after loss, the producer is detached with `incompatible` and `no keyframe within 2 s after video loss; restart the producer and set its keyframe interval to at most 2 s`. This bounds waiting, not successful decoder recovery.
- **Video-only interruption is status.** Once video has been seen, audio arriving after `stall_ms` without more video reports `interrupted` with reason `video_stalled`. Audio keeps the producer active, so this reason alone does not expire the session. A fully stalled attachment can be replaced by a compatible new `hello`; the old connection receives `detached` with reason `replaced`. A healthy attachment remains busy.
- **Idle after a detach is a switch** (`[serve] idle`), because Discord documents nothing about idle Go Live. Idle frames are sent only once a producer has detached; while an attached producer is stalled, nothing is sent:
  - `documented` (default): five Opus silence frames `F8 FF FE`, 20 ms apart, then nothing. Discord documents the five frames for voice connections; the spacing is the frame's own duration (RFC 6716 config 31). The frame is mono, which is valid in a stereo stream.
  - `none`: nothing.
  - `continuous`: a silence frame every 20 ms. Undocumented; kept as an experiment.

  Idle catch-up after a scheduling delay is limited to the latest 500 ms. Which mode Discord needs has not been measured yet. `documented` stays the default until a manual test against real Discord settles it; the result goes here and into `docs/specs.md`.

### IPC

- **A local stream behind one trait**, in a new crate `dstreamy-ipc`. No auth tokens.
  - Linux and macOS: a Unix socket in a 0700 directory (`$XDG_RUNTIME_DIR/dstreamy/` on Linux, the per-user directory from `confstr(_CS_DARWIN_USER_TEMP_DIR)` plus `dstreamy/` on macOS, not environment `TMPDIR`; a base directory or any of its parents that another user can write is rejected). When that is unset or the path is too long for `sun_path`, the fallback is a directory under the user's home (`~/.local/state/dstreamy/` on Linux, `~/Library/Application Support/dstreamy/` on macOS), never `/tmp`: in a world-writable directory another user could create the name first, block the service and impersonate it. An explicit endpoint has the same trust requirements: its immediate parent must be owned by us with mode 0700, and its ancestors must be trusted; `/tmp` is not a supported override. Both sides check the directory (owned by us, mode 0700, not a symlink) and the peer's uid with `peer_cred`. The server drops other users before anything is read; the client refuses a server running as another user. A lock file in the directory covers the remove-stale-then-bind step, so two `serve` starting at once can't orphan each other.
  - Windows: not built (see Deferred). `dstreamy-ipc` fails to compile off Unix.
- **The same wire format on every transport.** A connection starts with one JSON `hello` line naming its role.
  - `control`: NDJSON with the protocol 1 commands and error codes, plus `status` and `subscribe`, as `protocol: 2`. A client asking for a higher protocol gets `unsupported_protocol`. Lines are capped at 1 MiB; blank lines are skipped, and a trailing `\r` is accepted. A subscriber that falls behind is disconnected with `lagged` (an error with `"id":null`).
    - A control `hello` with protocol 1 or 2 is accepted, any other is `unsupported_protocol`; the reply is `{protocol, version, platform, connection, features, status}`, where `connection` is this connection's id and `features` lists what this serve supports beyond protocol 2 as first released: `start_grace_secs`, `status_place`, where it can open the login window `browser_login`, and unless its token comes from `DSTREAMY_TOKEN` `accounts` (the account commands of ADR 0005). Older builds omit `features`. Every build reports the same `version`, so a client cannot tell them apart by it, and protocol 2 stays 2 because both additions are optional.
    - `status` returns `{session, source, stats, started_by}`, each `null` when absent: the `SessionState` (with `guild_id`, `channel_id`, `channel_name` and `target`, as of the session's `start` or its last channel move, until it stops; `channel_name` is the name at that time, and `null` after a move to a channel the guild cache does not list; successful `stop` replies, and a `start` sets the new place, only after prior session-event publication is confirmed, including a run that stopped itself, so a late move of that run never moves the new place; an unconfirmed 2 s drain returns `busy` instead of acknowledging Stop or starting a new run), the external source (`{state: "detached"|"producing"|"interrupted", attachment?, reason?, for_ms?}`), the last `StreamStats` (its `viewers` as in the producer's `viewers` event), and the id of the connection whose `start` began the live session. `subscribe` adds `source` events of the same source shape with `"event":"source"`. Only `status` adds `source.stats`: `skipped` counts frames not forwarded because they came before `CaptureSource::start`, during a restart or before the keyframe gate opened; `dropped_video` and `dropped_audio` frames lost to a full source queue; `queued` the source queue's length now and `max_queued` its highest; `overflow_keyframe_requests` keyframes asked for after such a loss. All count over every attachment of the session.
    - A successful explicit `stop` replies with terminal `StreamStats` and consumes the cached statistics, so later `status.stats` is `null`, including after delayed state or health events. A stream that stops on its own retains its terminal statistics for `status`; a successful new `start` resets the cache for that run. If terminal-event publication cannot be confirmed within 2 s, `stop` instead replies `busy` without consuming those statistics, even though media may already be stopped. An idle or repeated Stop remains `not_running`. `start` also replies `busy` if any session event is published during its preparation, before creating the new capture or Go Live run. These checks use existing replies and events; no wire epoch or terminal health event is added.
    - `login` opens the browser login window (`dstreamy login --browser`) in a child of serve, with serve's config directory, so the next Discord connection reads the new token without a restart; an idle connection made with the old token is closed. It takes an optional `env` object with the client's `DISPLAY`, `WAYLAND_DISPLAY`, `XAUTHORITY`, `XDG_SESSION_TYPE`, `XDG_CURRENT_DESKTOP` and `DBUS_SESSION_BUS_ADDRESS`: a serve started by the user's service manager may lack the graphical session, and every name the object lacks is unset for the window. It takes an optional `account` to save into (ADR 0005). It replies with `{username, global_name, account}` once logged in, or `login_cancelled`, `login_failed` (with the reason), `login_running` (one window at a time), `streaming` or `login_unavailable`. The window closes after 10 minutes, or when the client that asked for it disconnects. A login that lands while a session streams applies once that session is over. `env` names outside that list are `invalid_params`. Only a serve built with browser login on Linux or macOS, without `DSTREAMY_TOKEN` in its environment (that token would win over the saved one), adds `browser_login` to `features`; a client offers the login only then.
    - Limits: 64 admitted connection groups, 10 s for the `hello` line, and at most 64 combined queued replies and running commands per control connection, beyond which the service stops reading from it. A connection's admission slot remains reserved while its disconnected command group, lagged-client flush or detached post-login update still runs, so reconnecting cannot bypass the limit. Further connections are sent a `busy` error and closed; beyond 64 such refusals in flight they are dropped unanswered. These are admitted-work limits, not a whole-process memory bound. Shutdown stops admission, aborts and awaits orphaned command groups, then shuts down the engine. A detached post-login update keeps its shared permit until completion or runtime cancellation; it is not an additional joined orphan group.
    - Protocol 1 `daemon` treats `external` like any other target it cannot capture.
  - `producer`: after `attached`, binary frames `u32 BE length | u8 kind | i64 BE pts_us | u8 flags | payload`. `length` counts everything after itself (the 10 bytes of kind, pts and flags plus the payload) and is at most 8 MiB. Kind 1 is an Annex B access unit, kind 2 an Opus packet, kind 3 end of stream; flag bit 0 marks a keyframe and is ignored on non-video frames. The other flag bits are reserved and must be 0, and an end-of-stream frame has no payload; both are rejected otherwise. pts is signed because OBS pts can be negative (Opus priming). The service answers with NDJSON events: `keyframe_request`, `source`, `viewers`, and `detached` with a reason. `viewers` carries `count`, the session's Discord viewers other than the streaming account, or `null` while unknown (before Discord reports them, and while the session is not streaming); it is sent on attach when known and on every change. `health` reports the live stream for a status display: `reconnecting`, `reconnects` (times this stream went reconnecting plus voice and stream connection resumes), `dropped_video` (video frames lost after the producer sent them: by this attachment's source queue and on the way to Discord), `audio_dropouts` (intervals of this stream in which fewer than half the expected Opus frames, 25 of 50, reached Discord, excluding intervals containing whole-source detachment or stall and the interval in which it resumes; video-only `video_stalled` does not suppress audio-dropout counting), and the last one-second interval's `audio_per_sec` (Opus frames sent to Discord), `fps`, `jitter_p95_ms`, `jitter_max_ms` and `bitrate_kbps`, plus `audio_level` and `video_level` (`good`, `warn` or `bad` over the last ten intervals); the interval figures and `audio_dropouts` are `null` until the first interval. It is sent on attach when a stream runs and on every change, at most about once a second. It also carries `e2ee` (`unknown`, `encrypted`, `unencrypted`) and `dave_protocol_version` (an integer, or `null` while unknown). The version is not proof of encryption: `encrypted` means DAVE is ready, while `unencrypted` means only hop-by-hop SRTP. It is only `{"type":"health"}` before the first stream reaches `Streaming`, including while `Connecting`, and after it stops. Reconnecting retains the counters but resets encryption to unknown until reported again. A producer that predates it, or a service that doesn't send it, leaves those figures unknown. A producer ignores event types it doesn't know, so the service can add events without a new protocol. The detach reason is `replaced` when a stalled producer is superseded, `oversized` for a frame over 8 MiB, `incompatible` for any other frame or ingest violation, `shutdown` when the service stops and `stopped` when the session lets go of the source; `detached` also carries a `message`, and the service then closes the connection. An end-of-stream frame, or the connection ending mid-frame, closes the attachment without a `detached` event. A producer `hello` whose `video` or `audio` objects or their fields are missing or mistyped is `invalid_params`; `malformed` stays for line-level faults and a hello without `protocol` or `role`.
  - Golden fixtures pin both roles, and the Rust and C sides decode the same files.
- **Ingest is validated against the specs:**
  - Annex B start codes are required.
  - A keyframe carries an IDR slice and SPS and PPS.
  - pts equals dts, so no B-frames.
  - Opus packets total 20 ms and are at most 1500 bytes. The per-packet stereo bit is not checked, because it is per packet.
  - pts never jumps forward by more than 10 s on either track. A track's first frame is measured against the other track's last pts.
  - A failure detaches the producer, and the session enters the grace period.

### OBS plugin

- **Written in Rust**, built as a `cdylib` inside the `obs-plugintemplate` CMake project (template build raised to OBS 32.2.2), against libobs bindings generated with bindgen from the pinned headers. A crash in a plugin takes OBS down, so the plugin core is memory-safe Rust, and it reuses the service's crates directly: the IPC codecs, the producer frame rules and the packet conversion are one implementation, not a C copy kept in step through fixtures. Every function libobs calls catches panics, so none unwinds into OBS. Only the status-bar panel and the settings dialog are C++/Qt, in one file under `obs/ui/`, because they are `QWidget`s. The plugin holds no Discord, token or WebRTC code, connects to a running `serve` and never spawns or owns it.
- **A separate output, next to the normal stream.** The plugin registers the encoded output `dstreamy_output` and starts and stops it itself, from:
  - a status-bar panel (`statusBar()->addPermanentWidget`, calling into the Rust core) with Start/Stop, the session state and the health counters, and a settings dialog opened from Tools > D-Streamy… with the server and voice channel picker, the account row and the audio track settings (ADR 0007). A dock was the first design; see Deferred.

  OBS's stream service stays free for Twitch or any other service, and starting or stopping one never affects the other. Settings › Stream couldn't host a third-party service anyway: it offers only custom RTMP, the built-in services and WHIP.

  The panel warns visibly when the service reports an unencrypted stream; health details include the reported DAVE version. Missing or unfamiliar encryption states remain unknown, and reconnecting clears the reported encryption state to unknown. Audio packets lost in the OBS ring appear separately in the audio details; they are not added to video-frame losses or to the service's audio-dropout interval count. If the output ends but ending its Discord session fails, the warning and Stop control remain through reopening and list-refresh errors until a successful Stop.
- **Test control.** Tests drive the plugin through the `test-hooks` cargo feature (`rust/crates/dstreamy-obs/src/hooks.rs`): output settings and `DSTREAMY_TEST_*` variables that force panics, delays and fake service answers. The CMake option `DSTREAMY_PLUGIN_TEST_HOOKS=ON` enables it, and `obs/cmake/common/check_test_hooks.cmake` checks that a shipped plugin contains none of those names. The obs-websocket vendor of the first design was not built; see Deferred.
- **Encoders:**
  - Audio is always the plugin's own `ffmpeg_opus` encoder (960-sample frames), because the stream service usually needs AAC.
  - Video defaults to the plugin's own H.264 encoder, bound to the canvas (`obs_encoder_set_video`; audio with `obs_encoder_set_audio`): no B-frames, `keyint_sec` 2, scaled down to fit 1920×1080 with even dimensions on the GPU (`obs_encoder_set_gpu_scale_type`, so texture encoders like NVENC and VAAPI keep their GPU path). The frame rate is 15, 30 or 60 via `obs_encoder_set_frame_rate_divisor`: a 60 fps canvas allows 60, 30 or 15, a 30 fps canvas 30 or 15. 24, 25, 50 and NTSC (30000/1001) canvases have no valid divisor and are reported with the setting to change.
  - Optionally the stream's video encoder is shared, if it meets the same rules: H.264, no B-frames, `keyint_sec` in [1, 2], even size up to 1920×1080, FPS 15, 30 or 60, a color format of exactly NV12 or I420, and custom options that pass the encoder check (`x264opts` for x264, `opts` for NVENC, `ffmpeg_opts` for VAAPI, AMF and OpenH264). x264 permits only whitespace-separated numeric `scenecut=0..100` and `aq-mode=0..3` options; custom profile, preset and tune overrides are refused. Other families refuse recognized B-frame, keyframe-interval and Annex B/header override keys. B-frames are the encoder's effective count, computed the way its plugin applies its settings: for x264, the preset and tune (matched exactly, as obs-x264 does), then a user-set `bf`, then the profile (`baseline` zeroes them unless the input is 4:4:4 or the rate control is lossless); for NVENC, `bf` raised to at least 4 by the Ultra High Quality tuning; for QSV, a user-set `bf` over `bframes`; for VideoToolbox, the `bframes` switch. This is a start-time prediction; the pts ≠ dts guard below stays authoritative. Otherwise the plugin falls back to its own encoder, or errors if the user chose that.
  - Sharing is only possible while the main stream is active. libobs keeps the two outputs independent (each has its own callback and waits for its own first keyframe), but the frontend owns the encoder: it has no video until streaming was set up once, it rebuilds encoders on a Settings Apply, and it changes the encoder's bitrate while streaming. So share mode follows `OBS_FRONTEND_EVENT_STREAMING_STARTING` and `_STOPPING` (STARTED fires only after the remote connect, and never on a failed one) and switches to the plugin's own encoder when the main stream stops. One encoder error stops both outputs.
  - A runtime guard rejects any packet with pts ≠ dts.
- **The OBS threads are never blocked.**
  - `encoded_packet` runs on the encoder thread, under mutexes shared with audio and with every output fed by the same encoder. In both modes a blocking call stalls the user's main stream too (the audio encoder or, in share mode, the video encoder is shared). It only copies the packet into a bounded ring (256 packets or 32 MiB, ADR 0009) and returns; a writer thread does the IPC. When the ring is full, older video groups are evicted while preserving the newest queued decodable group where possible; otherwise video waits for a new keyframe. Oldest audio is dropped first where space can be reclaimed (ADR 0009).
  - Start runs the connect, `hello` and control `start` on a thread, as OBS's RTMP output does.
- **SPS/PPS** are taken from the encoder's extra data and prepended to any keyframe that lacks them. Extra data is read lazily, because NVENC, VAAPI and VideoToolbox only provide it after their first packet. x264 repeats them in-band by default, but `x264opts` can turn that off, so the plugin never relies on it. Extra data in avcC form (possible from third-party encoders) is rejected.

### Keyframe requests

libobs has no public API to request a keyframe from an encoder. Some encoders (NVENC, AMF) emit an IDR as a side effect of a settings update; that is per encoder, undocumented as an interface, and would disturb a shared stream, so it is not used. That leaves every keyframe request unanswered, not only Discord's:
- viewer PLI and FIR, surfaced by our transport;
- the pump's own requests: on every attach after a reconnect or channel move, 500 ms after DAVE comes up (davey may reject the first keyframe), and on queue overflow or a lost frame.

They are logged, and the `keyframe_request` event still reaches the producer so a future encoder that can honour it may. Configured keyframes at most 2 s apart limit the normal wait only while the encoder actually emits them. A missing keyframe does not guarantee decoder recovery; after source loss the 2 s timeout detaches instead, as above.

For PLI this is conformant, since RFC 4585 makes a reaction optional. For FIR it deviates from RFC 5104 §4.3.1.2, which requires a refresh point. This is accepted deliberately.

### Supervision

`dstreamy service install|uninstall|status|print`, user-level, no root or admin. Linux only today: a systemd user unit in `~/.config/systemd/user` with `Restart=on-failure` and `RestartSec=2`. On any other platform the command fails with `unsupported_platform`; the macOS and Windows backends are listed under Deferred.

A service restart ends the Discord session; no session state survives process death.

### Platforms

Linux and macOS capture and service implementations are present, with CI workflows for both. Workflow definitions alone do not establish successful runs or hardware coverage. Windows is deferred to issue 15: `dstreamy-ipc` is a `compile_error!` off Unix, `dstreamy service` reports `unsupported_platform` off Linux, `rust-ci.yml` has no Windows job, and the plugin builds on Windows without the service connection and tells the user so. When Windows comes, `dstreamy` streams there only from an external producer and the test pattern; no native capture backend is added.

Unix-only code lives behind `cfg(unix)`: the 0600 token and config files (`config.rs`), logging, and signal handling (`signals.rs`). Windows needs equivalents: an ACL that limits the token and config files to the current user, and Ctrl-C, close and shutdown events that stop `serve` like SIGTERM. New Unix-only code stays inside `dstreamy-ipc`, the plugin's IPC module and the service installers.

## Consequences

- OBS can stream to Discord and to Twitch at the same time, and either can stop independently.
- The directory trust check reads owner and mode bits only. On macOS, an ACL on a parent directory can grant another user write access without changing the mode; only the owner or root can set it, and `~/Library` carries a standard deny ACL, so refusing every ACL would break the home fallback. This is accepted.
- Flatpak OBS can't reach the service's socket in its default sandbox, so the first release supports native OBS packages only; Flatpak needs a later decision on a sandbox-visible socket path or a documented override.
- An OBS crash or restart within the grace period keeps the Discord stream; the viewer sees a short freeze, then picture from the next keyframe.
- The default own-encoder mode costs a second video encode, and a hardware encoder may hit the driver's session limit. Share mode avoids that but works only while the main stream runs and constrains its encoder; a Twitch encoder error ends both streams.
- After viewer loss, a reconnect, a channel move or a DAVE transition, picture recovery waits for an actual decodable keyframe. Normally this is the configured interval, possibly another if DAVE drops the first; encoder stalls and missing keyframes invalidate a fixed recovery bound.
- Each new producer attachment re-announces its size and frame rate, so a restarted OBS with a different canvas is shown correctly.
- If a new producer's audio/video skew is smaller than the previous one's, both tracks start that much ahead of the clock, once, because one shared offset can't move either track backwards. OBS's skew comes from fixed encoder priming, so reconnects with the same settings don't trigger it.
- `daemon`'s wire format and protocol 1 fixtures are unchanged; `start` can additionally fail with `already_running` when another process holds the session lock. The macOS app keeps working as is.
- The idle and grace defaults are provisional until a manual test against real Discord measures them.
- OBS CI defines source builds on Linux, macOS and Windows. The baseline is 32.2.2, with a separate Linux plugin compatibility job at 33.0.1. The release workflow defines preview packages and optional signing; no published tag, completed rehearsal or signing execution was observed during this reconciliation. A CI spike showed libobs runs headless on the Linux, macOS and Windows runners (software rendering; Linux needs `xvfb-run`), and the full OBS frontend with obs-websocket starts headless too, those historical measurements do not prove the current full plugin suite passes on all three.

## Deferred

Decided here, not built. Each item names the state today.

- **Windows** (issue 15). The IPC transport was to be the named pipe `\\.\pipe\dstreamy-<user SID>`, created with `FILE_FLAG_FIRST_PIPE_INSTANCE`, a DACL for the current user only and remote clients rejected, both sides checking each other's token user (`GetNamedPipeClientProcessId`, `GetNamedPipeServerProcessId`). Supervision was to be a Task Scheduler logon task with `LogonType=InteractiveToken`, `ExecutionTimeLimit=PT0S`, no battery restrictions and `IgnoreNew`; whether `RestartOnFailure` restarts a killed process is undocumented, and `serve --supervise` would respawn the service if not. Today `dstreamy-ipc` is a `compile_error!` off Unix, `dstreamy service` fails with `unsupported_platform`, and the plugin on Windows shows "not supported on Windows yet" with Start and Stop disabled.
- **macOS launchd agent** for `dstreamy service`: `KeepAlive {SuccessfulExit: false}`, `RunAtLoad`, `ThrottleInterval` 2 (the default is 10 s). Today `service/` holds only `systemd.rs`; on macOS the user runs `dstreamy serve` by hand.
- **A dock** (`obs_frontend_add_dock_by_id`). Replaced on 2026-11-05 by the status-bar panel and the Tools > D-Streamy… settings dialog (ADR 0007). The Rust model types still carry `Dock` in their names until renamed.
- **An obs-websocket vendor `dstreamy`** with `start`, `stop` and `status` requests, for test control. obs-websocket's `StartOutput` was not enough: it needs the output under a stable name, bypasses the UI and reports no failure. Tests use the `test-hooks` feature instead, so nothing registers a vendor and `obs-websocket-api.h` is not vendored.
- **"Start and stop with Start Streaming"** as an option: not built. Share mode (the stream's encoder) exists; an automatic start does not.

## Rejected

- **OBS as the stream service** (a custom service on the `DSTREAMY` protocol, selected from the Tools menu). It occupies the only stream service slot, so the user can't stream to Twitch at the same time, and saving Settings › Stream replaces it.
- **Discord transport inside the OBS plugin.** It would tie the stream's life to OBS's process and put the token into OBS.
- **The plugin in C.** It would duplicate the IPC codecs and the packet rules in a second language, and a memory bug in it crashes OBS; a review of an early C packet converter found two NULL dereferences and a parameter-set ordering bug that breaks decoding.
- **RTMP or another media server between OBS and `dstreamy`.** It adds a hop, a protocol and its latency for no gain over a local socket.
- **Per-track timestamp rebasing.** It desyncs audio and video by the gap length, because the pump does not pace by wall clock.
- **A token or password on the local socket.** It adds secret handling without adding protection beyond the per-user directory, the DACL and the peer check.
- **Replaying a cached keyframe from the plugin on a `keyframe_request`.** Once later delta frames went out, an old IDR with its old pts breaks the monotonic timeline, and the same IDR restamped as current breaks the reference chain of the deltas that follow. The ring keeps the newest queued GOP whole, but nothing already sent is replayed; recovery waits for an actual new keyframe, subject to the loss timeout and qualifications in Keyframe requests.
